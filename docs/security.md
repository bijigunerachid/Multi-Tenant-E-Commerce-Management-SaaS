# Security design

Threats are listed in rough order of impact for a multi-tenant SaaS, each with the control
that addresses it and how the control is tested.

| #   | Risk                                                                                                                    | Control                                                                                                                                                                                                                                                                                                                                                                                                          | Verified by                                                                                                                                                                                                              |
| --- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **Cross-tenant data access (IDOR)**: guessing or swapping an ID in a URL or body to read or change another org's record | Tenant comes from the session only. Tenant handlers query through `req.db` (`tenantDb`), which injects `organizationId` and throws on a foreign one. A record from another org returns **404**, not 403, so its existence is not revealed. Composite FKs stop cross-tenant links. Every route is declared with an access rule, and the isolation suite requires a cross-tenant fixture for every route parameter | An isolation test suite: two orgs; every route is called with the other org's IDs in path, query and body, including nested routes (`/orders/:id/items/:itemId`) and links (an order line pointing at a foreign variant) |
| 2   | **Broken function-level authorization** (an analyst calling a write route)                                              | `authorize(permission)` on every route. A route test fails if any registered route has no permission (or is not explicitly public)                                                                                                                                                                                                                                                                               | Role matrix tests: each role × each protected route → expected status                                                                                                                                                    |
| 3   | **Privilege escalation through roles**                                                                                  | Only owners grant `OWNER`. Nobody changes their own role. The last active owner cannot be removed or demoted. Super admin exists only through a server CLI                                                                                                                                                                                                                                                       | Tests for each rule                                                                                                                                                                                                      |
| 4   | **Session theft or fixation**                                                                                           | Opaque 256-bit session ID; a new ID on login and on privilege change; `HttpOnly`, `Secure` (prod), `SameSite=Lax`, `__Host-` cookie prefix in prod; idle timeout (2 h) and absolute timeout (7 d); logout deletes the server session; password change revokes other sessions                                                                                                                                     | Auth integration tests                                                                                                                                                                                                   |
| 5   | **CSRF**                                                                                                                | Per-session token in `X-CSRF-Token` on POST/PUT/PATCH/DELETE, plus an `Origin` allowlist. The Stripe webhook is exempt and authenticated by signature                                                                                                                                                                                                                                                            | Tests: a write without the token gets 403                                                                                                                                                                                |
| 6   | **Credential attacks**                                                                                                  | Argon2id. Login rate limit per IP and per account (Redis). The same error message and similar timing for "no such user" and "wrong password". Password policy: at least 10 characters, checked against a common-password list                                                                                                                                                                                    | Rate-limit and enumeration tests                                                                                                                                                                                         |
| 7   | **Password reset and invitation abuse**                                                                                 | 32-byte random tokens; only their SHA-256 is stored; single use; short TTL; the reset request always answers 202 (no account enumeration); invitations are bound to the invited email                                                                                                                                                                                                                            | Token reuse and expiry tests                                                                                                                                                                                             |
| 8   | **Overselling and inventory corruption**                                                                                | Atomic conditional updates; DB `CHECK` constraints; one transaction per operation; reservation status guards                                                                                                                                                                                                                                                                                                     | Concurrency test: 20 parallel orders against stock of 5 → exactly 5 succeed, stock never goes negative                                                                                                                   |
| 9   | **Forged payment success**                                                                                              | Subscription state changes only from Stripe webhooks with a verified signature (raw body). Idempotent by event ID. Redirect query strings are ignored                                                                                                                                                                                                                                                            | Webhook tests: bad signature → 400 and no change; replay → no-op; `invoice.payment_failed` never activates                                                                                                               |
| 10  | **Injection**                                                                                                           | Prisma parameterized queries. Raw SQL only through tagged `Prisma.sql` templates; sort fields come from allowlists. React escapes output; no `dangerouslySetInnerHTML`                                                                                                                                                                                                                                           | Lint rule plus review; tests with hostile sort and filter values                                                                                                                                                         |
| 11  | **Malicious uploads**                                                                                                   | Images only (JPEG/PNG/WebP, checked by magic bytes, not by name or client MIME type); 5 MB and 10-per-product caps; random storage key generated by the server and checked against path traversal; stored outside any web-served folder; served only through an authenticated, tenant-scoped API route with the stored `Content-Type`, `nosniff` and `Content-Disposition: inline`                               | Upload tests with spoofed types                                                                                                                                                                                          |
| 12  | **Abuse and denial of service**                                                                                         | Body size limits; pagination max 100; Redis rate limits; date range limits on reports; CSV exports run as background jobs                                                                                                                                                                                                                                                                                        | Tests for limits                                                                                                                                                                                                         |
| 13  | **Information leakage**                                                                                                 | Central error handler returns generic messages plus a request ID; stack traces only in server logs; secrets redacted in logs; `helmet` headers; strict CORS                                                                                                                                                                                                                                                      | Test: a forced 500 response contains no stack trace                                                                                                                                                                      |
| 14  | **Secrets exposure**                                                                                                    | Environment variables validated with Zod at startup; `.env` is git-ignored; only `VITE_` variables reach the browser, and none of them are secret; Docker images are built without `.env`                                                                                                                                                                                                                        | CI runs `npm audit --omit=dev --audit-level=high` and scans the whole git history with gitleaks (`.gitleaks.toml` allows only fake test keys)                                                                            |
| 15  | **Suspended or deactivated users keep access**                                                                          | Membership and org status are checked on every request (short cache, invalidated on change)                                                                                                                                                                                                                                                                                                                      | Test: deactivate → the next request is rejected                                                                                                                                                                          |
| 16  | **Job-queue tenant confusion**                                                                                          | Email jobs carry only a delivery id and the rendered message; notification delivery reads outbox rows written by tenant-scoped code, and every worker query filters on that row's organization                                                                                                                                                                                                                   | Worker unit tests                                                                                                                                                                                                        |
| 17  | **Unaudited sensitive changes**                                                                                         | Audit log (append-only trigger) for auth events, role changes, invites, ownership transfer, stock adjustments, cancellations, exports, billing changes and admin actions                                                                                                                                                                                                                                         | Tests check that the audit rows exist                                                                                                                                                                                    |

## Production hardening

- **Edge.** Caddy terminates HTTPS (certificates obtained and renewed automatically) and sends
  `Strict-Transport-Security`, a strict `Content-Security-Policy` (scripts, styles, fonts and
  connections from the site's own origin only; no framing), `X-Frame-Options: DENY`,
  `X-Content-Type-Options`, `Referrer-Policy` and `Permissions-Policy`. The web app never loads
  third-party resources: fonts are served with it and not inlined (an inlined font was found
  blocked by the policy during the production test and fixed).
- **Network.** Only ports 80 and 443 are published. The API, worker, PostgreSQL and Redis share
  a private network; Redis requires a password and never evicts keys.
- **Containers.** The API, worker and web server run as unprivileged users. Images are built
  without install scripts, from pinned base images, and never contain `.env` files, tests or the
  git history (`.dockerignore`).
- **Configuration.** In production the API refuses to start with plain-http `APP_URL`, an
  `APP_URL` missing from `CORS_ORIGINS`, the in-memory or default local mail settings, or a
  `RATE_LIMIT_SCALE` other than 1; outside production it refuses live Stripe keys.

## Row-Level Security: evaluated, not enabled (yet)

Isolation between organizations relies on three layers today: the session decides the tenant
(no request field can name it), `tenantDb` adds `organization_id` to every query on a tenant
model and throws when a query names another organization, and composite foreign keys make the
database refuse cross-tenant references. Generated tests send every route another
organization's ids, and sabotage checks showed each layer is caught when removed.

PostgreSQL Row-Level Security would add a fourth layer: a policy `organization_id =
current_setting('app.organization_id')::uuid` on each tenant table, so even a forgotten filter
in raw SQL returns nothing. It was evaluated and deferred, for these reasons:

- **Every query must run inside a transaction that sets the tenant** (`SET LOCAL`). With Prisma
  that means wrapping each request in an interactive transaction, holding a pooled connection
  for the whole request, which costs throughput and risks pool exhaustion under load.
- **Cross-tenant code is legitimate in a few places**: the worker (notification outbox, trial
  expiry), the Stripe webhook, platform administration and the reports' raw SQL. Each would need
  a separate database role with `BYPASSRLS`, or explicit per-organization switching.
- **The app connects as the table owner**, which bypasses RLS unless `FORCE ROW LEVEL SECURITY`
  is set; enabling it safely needs a dedicated, non-owner application role and migrations run as
  the owner.

**When to enable it:** before a second team writes code against the database, or before raw SQL
grows beyond the reports and inventory modules. The path is ready: a non-owner `vendora_app`
role, `FORCE ROW LEVEL SECURITY` with policies on the tenant tables, `SET LOCAL
app.organization_id` in the request transaction, and a `vendora_worker` role with `BYPASSRLS`
for the cross-tenant jobs.
